# 描画の軽さ

視点を回す・家具をドラッグするときに「かくかく」しないための仕組みと、その裏付けになった計測のまとめ。
新しい描画処理やアセットを足すときは、最後の「足すときのチェックリスト」を見る。

## 1. どこが重かったか

計測は `?perf` の動作診断（→ 5 章）。代表的な環境は WQHD モニター（2560×1271 のキャンバス、dpr 1）＋ Intel Arc 140T（内蔵 GPU）、家具 54 点・メッシュ約 860・三角形約 18 万の部屋。

| | 対策前 | 対策後 |
|---|---|---|
| 視点を一周（fps） | 36 | 60（画面の上限） |
| 〃 GPU ms / フレーム | 27 | 11 |
| 〃 ドローコール / フレーム | 1375（うち影 824） | 約 690（影はほぼ 0） |
| ドラッグ中（fps） | 30 未満、ときどき 80〜280ms 止まる | 60 |
| 〃 CPU ms / フレーム | 20〜25 | 5 |

わかったこと：

- **CPU はほとんど余っていて、GPU が重い。** 視点を一周するあいだ CPU は 4〜5ms、GPU は 25ms 以上。
- **GPU の重さは「物の数」より「画素の数」で決まる。** 家具が画面外に出てドローコールが 330 まで減った角度でも、GPU は 22ms から下がらなかった。2560×1271 ＝ 約 325 万画素を 1 枚ずつ塗る処理（AO・SMAA・光・影の参照）が大半。
- **GPU の内訳**（対策前）：AO 17ms ＞ 本体の描画 6ms ＞ 影の描き直し 1.6ms ＞ 仕上げ（SMAA など）1.3ms。
- **ドラッグ中だけの重さは JavaScript 側にあった。** 線のシェーダーを 1 歩ごとに作り直していた（→ 2-3）。

## 2. 考え方

1 秒あたりの描画コスト ＝ **描く回数** × **1 回あたりの重さ**

1 回あたりの重さはさらに、**画素の数 × 1 画素の重さ**（AO・ライティング・ポストエフェクト）と、**物の数 × 1 個の重さ**（ドローコール・CPU の準備）に分かれる。施策もこの 2 つの軸で整理する。

- **A. 描く回数を減らす**：変わっていないものは描き直さない、作り直さない。
- **B. 1 回あたりを軽くする**：塗る画素を減らす、1 画素の処理を軽くする、物の数を減らす。

どちらも「止まっているときの見た目は変えない」ことを条件にする。軽くするのは、見た目の細かさに目が行かない「動いている間」だけにする。

## 3. A. 描く回数を減らす（変わったときだけ描く）

### A-1. 画面はオンデマンドで描く（既存）
`frameloop="demand"`。止まっているあいだは 1 枚も描かない。CameraControls・React のプロパティ変更・`invalidate()` で描く。`useFrame` で動かし続けるもの（ぽよん・キー移動・自動一周）は自分で `invalidate()` する。

### A-2. 影マップは、影が変わったときだけ描き直す
`src/three/render/ShadowOnDemand.tsx`

太陽の影は視点に関係ないので、視点を回すだけなら影マップ（4096²、影を落とす物ぜんぶを描く）は描き直さなくていい。`gl.shadowMap.autoUpdate = false` にして、毎フレーム「影を落とす物の id・形・素材・ワールド行列と、影を出すライト」を数値の列にして前と比べ、違ったときだけ `needsUpdate` を立てる。

- **効果**：視点を回すときのドローコールがほぼ半分（1375 → 約 690）、GPU 約 −2ms。
- **印を手で付ける方式にしない理由**：ぽよん・ドラッグ・壁の透け・時間帯など、物が動く経路が多い。付け忘れると影が置いていかれるので、比べる側で全部拾う。
- 家具のドラッグ中は物が動くので毎フレーム描き直す（正しい動き）。

### A-3. シェーダーは作り直さない
`src/three/Line.tsx`

drei の `<Line>` は `points` が変わるたびに、ジオメトリと一緒に**マテリアルまで dispose する**。three.js は使い手がいなくなったシェーダーを捨てるので、ドラッグの 1 歩ごとに線のシェーダーをコンパイルし直していた（ANGLE/D3D11 で 1 回数十 ms）。自前の `Line` はマテリアルをコンポーネントが生きているあいだ使い続け、ジオメトリだけ差し替える。

- **効果**：ドラッグ中の CPU 20〜25ms → 5ms、80ms 級の長いタスクがなくなった。
- ドラッグ中だけ出る線（寸法・スナップ）も、出し入れのたびに作り直さないよう、常に置いたまま `visible` で隠す。`key` に座標を入れない（入れると毎回作り直しになる）。

## 4. B. 1 回あたりを軽くする

### B-1. 動いている間だけ、塗る画素を減らす
`src/three/render/MotionQuality.tsx`・`renderScale.ts`

視点の回転・ズーム・パン・歩く・家具のドラッグをしているあいだだけ、コンポーザー（AO・SMAA などの後処理）の内部バッファを約 180 万画素（`MOTION_PIXELS`）に縮めて描き、最後のパスでキャンバスいっぱいに引き伸ばす。入力が終わった瞬間（ポインタを離す・キーを離す・ホイールが 160ms 止まる・ドラッグ終了）に元の大きさで描き直す。

- **効果**：WQHD で動いている間 0.7 倍（画素は約半分）になり、GPU 25 → 13ms。AO はほぼ画素の数に比例して減る。
- **倍率ではなく画素の総数で決める**：WQHD の dpr 1 はフル HD の 1.6 倍の画素がある。dpr だけ見ていると、いちばん効いてほしい大画面で何も起きない。高 DPI のノートは 1 倍まで、小さい画面はそのまま。
- **キャンバスの大きさは変えない**：dpr を下げてキャンバスを縮めると、サイズ変更で中身が消え、動き始めに一瞬白く抜ける。
- **画質を戻すのは「入力が終わった瞬間」**：カメラの慣性（イージング）が止まるのを待つと戻りが遅く感じる。慣性の最後はゆっくりなので、フル画質で描いても困らない。
- 入力したまま止まっていると描画も止まるので、400ms 描画がなければフル画質の 1 枚を描く。
- 止まった絵は、軽量化なしの描画と画素単位で一致することを確かめた。

### B-2. AO の品質
`src/three/render/quality.ts` の `AO_QUALITY`

N8AO の `high` は 1 画素あたり 64 サンプル。WQHD でフル解像度だと GPU 17ms と、いちばん大きな出費になる。`medium`（16 サンプル）にすると AO は 1/3 程度になり、見た目は 1.5 倍に拡大して並べてもほぼ見分けがつかない（平均の差 1.4/255、接地の縁がわずかにやわらかくなる）。`low` は粒が見え始める。

- **いまの設定は `high`**（止まっている絵の質を優先）。B-1 のおかげで、動いている間も 60fps に収まっている。
- もっと軽くしたいときに最初に下げるのはここ。

### B-3. 物の数を減らす（保留）
家具ごとに、同じ素材の部品を 1 つのメッシュにまとめると、家具のメッシュは約 1/3（454 → 155）になる見込み。ただ、上の環境では CPU が余っていて、GPU は物の数にあまり左右されないので、効果は薄いと判断して保留している。CPU が弱い端末（スマホなど）で CPU 側が重いと出たら検討する。

## 5. 採用しなかったもの・罠

- **AO を動いている間だけ半解像度にする**（N8AO の `halfRes` を切り替える）：切り替えのたびにパスとターゲットを作り直し、長いフレームが出た。
- **Canvas の dpr を下げる**：キャンバスの中身が消えて白く抜ける。さらに `setDpr` で変えても、Viewport が再レンダーすると `dpr={[1, 2]}` に戻される（ドラッグ中は 1 歩ごとに戻っていた）。
- **時計だけで「止まった」と判断する**：1 フレームが判定時間より長い遅いマシンで、毎フレーム画質を行き来する。
- **SwiftShader（ヘッドレス）の数字を信じる**：GPU が 1 フレーム 1 秒以上かかる。絶対値ではなく、ドローコール・シェーダーのリンク回数・画素の一致など「数えられるもの」で確かめる。

## 6. 測り方

### `?perf`（動作診断）
画面上部のパネルから記録する。

- **自動で一周**：カメラが 6 秒で一周するあいだを記録する。毎回同じ動きなので、前後の比較に使う。
- **記録（5 秒）**：自分で動かしているあいだを記録する。ドラッグなど、自動一周では出ない操作を測るとき。

結果には、fps、フレーム間隔、1 フレームあたりの CPU と GPU の時間が出る。GPU は `EXT_disjoint_timer_query_webgl2` がある環境だけ測れる。

さらに **GPU の内訳**（本体・AO・仕上げ・影・その他）、ドローコール（影の分も）、動いている間の倍率、長いタスク、GPU 名、部屋の規模が出る。「ログをコピー」で JSON ごとコピーできる。

読み方：

- **フレーム間隔が 16.7ms 前後**：60Hz の上限に張り付いている。これ以上は測っても変わらない。
- **GPU ＞ CPU**：画素か物の数が重い。内訳で AO・本体が大きければ B、影が毎フレーム出ていれば A-2 を疑う。
- **CPU が大きい、または長いタスクがある**：JavaScript 側の処理。シェーダーの作り直しやデータの組み立てを疑う（A-3）。

GPU 時間の内訳は、タイマーのクエリが入れ子にできないので、フレームの頭から「その他」で計り始める。コンポーザーの各パスと影の描画に入るたびにクエリを切り替え、出るときに元へ戻す。

### `scripts/perf-check.mjs`（回帰チェック）
dev サーバー起動中に `node scripts/perf-check.mjs`。ヘッドレスで次を確かめる。

- ドラッグ中にシェーダーのリンクが起きない（A-3）
- ドラッグ中はキャンバスの大きさが変わらず、内部だけ縮む。離すと元に戻る（B-1）
- 家具を動かしたあとの影が最新（影マップを強制的に描き直しても絵が変わらない）（A-2）

### シェーダーの作り直しを見つける
`gl.getContext().linkProgram` を包んで回数を数える。何もコンパイルしないはずの操作で増えていたら、どこかでマテリアルを作り直すか、捨てている。`window.__oheya.perf.three()` から renderer と scene に触れる（`?perf` のときだけ）。

## 7. 足すときのチェックリスト

- **`useFrame` で動かし続けるもの**は自分で `invalidate()` する（A-1）。
- **影を落とす物を動かすとき**は、何もしなくていい（A-2 が拾う）。ライトを足すときは、影を出すなら `ShadowOnDemand` の比較に入っているか確かめる。
- **3D の線**は `src/three/Line.tsx` を使う。描画のたびにマテリアルを `new` しない。出し入れの多いものは `visible` で隠す（A-3）。
- **ポストエフェクトを足すとき**は、パスの `setSize` が内部バッファの大きさに従うこと（B-1 で縮む）を確かめる。
- **重くなった気がしたら** `?perf` の自動一周を前後で撮って比べる。
